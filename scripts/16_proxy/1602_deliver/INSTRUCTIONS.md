# 1602_deliver — комплект уезжает монтажёру

Подэтап отвечает только за перевозку: собранный и прошедший контракт комплект
попадает на Google Drive и становится самодостаточным. Байты здесь не делаются —
их делает `1601_build`.

## Что лежит

```
upload_proxies.sh   заливка комплекта проекта + добор WAV и транскриптов server-side
```

## Как залить комплект проекта

```
bash ~/YTAI/scripts/16_proxy/1602_deliver/upload_proxies.sh \
  "$PROJ/01_Source_Proxy" <PARENT_FOLDER_ID> <имя папки на Drive>
```

Скрипт делает четыре вещи:

- создаёт папку на Drive и льёт в неё прокси-видео;
- добирает петличные WAV из оригинальных сцен **server-side** — копирование в
  пределах одного remote трафика не тратит;
- добирает транскрипты тем же способом;
- сверяет `rclone check --size-only --one-way` и печатает ID и ссылку на папку.

## Правила, которые здесь легко нарушить

- **Лить на те же пути.** `rclone copyto` по существующему пути обновляет тот же
  файл: ID папок сохраняются, и ссылки, уже розданные монтажёру, остаются живыми.
  Новая папка вместо обновления — это мёртвые ссылки у всех, кому их отдали.
- **`--exclude "._*"` обязателен.** Тома exFAT плодят AppleDouble на каждый файл
  и папку; без исключения весь этот мусор уезжает на Drive.
- **`--tpslimit 6–8`.** Выше — 403 от Drive.
- **Оригиналы рекордера в комплект не входят.** Едут только сведённые
  `*_timeline.wav`; целые `*_orig*.wav` живут на Drive в `99_Pipeline/DJI_Audio/`
  и при надобности пересобираются `0113_frame_align.py` с SSD.
- **Спаннер копируем на Drive, а не льём дважды.** Клип, который нужен в двух
  сценах, кодируется один раз, вторая копия делается server-side.

## Ночная пересборка канала

Отдельной заливки не требует: `1601_build/rebuild.py` кодирует и льёт внахлёст,
удаляя локальный файл только после подтверждённой заливки. Этот подэтап нужен,
когда комплект уже собран локально и его надо просто отвезти.
