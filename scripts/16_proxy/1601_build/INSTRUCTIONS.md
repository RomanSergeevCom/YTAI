# INSTRUCTIONS.md — 1601 Build (сборка прокси-комплекта по контракту)

**Версия 1.0 · собрано 22.09.2026**

Полный рабочий процесс этапа. Человек может идти по нему вручную; агент — тоже,
шаг за шагом, не пропуская сухой прогон.

## Что это

Из `{project}/01_Source` собирается `{project}/01_Source_Proxy`: то же дерево
сцен, те же имена файлов, отличается только имя корневой папки. Каждый готовый
клип проходит гейт из восьми пунктов контракта; не прошёл — **в комплект не
уезжает** и попадает в отчёт отдельной строкой.

Что делать с клипом, решает `contract.py`, а не человек:

- `encode` — тяжёлый материал с камеры: HEVC 8 Мбит/с, битность и таймкод с источника
- `copy` — уже лёгкое (айфон) или есть недекодируемая дорожка: байт-в-байт
- `skip-symlink` — клип-спаннер, живущий симлинком во второй сцене: кодируем один
  раз, вторую копию делаем на Drive server-side

## Перед началом — загрузить знания (в этом порядке)

1. `project_knowledge/contract.md` — восемь пунктов, почему именно они, все замеры
2. `project_knowledge/ffmpeg_gotchas.md` — оплаченные грабли, симптом → лечение
3. шапка `contract.py` — то же в сжатом виде, плюс константы рецепта

## Окружение

```bash
ffmpeg -version | head -1     # ожидается 8.x; контракт проверялся на 8.1.1
python3 -V                    # системный подходит: проверено на 3.9.6
```

Venv не нужен: этап держится на стандартной библиотеке и вызовах
`ffmpeg`/`ffprobe`/`rclone` через `subprocess`.

## Шаги

### 1. План — `--dry-run`

```bash
P="/Volumes/T7-Beige-RYA/YTCH/YTCH12_Sveta"
B=~/YTAI/scripts/16_proxy/1601_build

python3 $B/proxy.py --src "$P/01_Source" --dst "$P/01_Source_Proxy" --dry-run
```

Сухой прогон снимает параметры дешёвым `probe_fast` (без счёта пакетов и без проб
звука) и печатает: сколько клипов пойдёт в `encode`, сколько в `copy`, сколько
пропустится, ожидаемый вес комплекта и свободное место на целевом томе.

**Читать надо две строки.** Первая — разбивка по действиям: если весь FX3 вдруг
попал в `copy`, значит материал уже пережат кем-то до нас. Вторая — место:
ожидаемый вес считается как исходник ÷ 18 для `encode` плюс полный размер для
`copy`; если свободного меньше, дальше идти нельзя.

### 2. Один клип — `--only` + `--gate-report`

Прежде чем гнать проект, прогнать один характерный клип каждой камеры и
посмотреть все девять строк таблицы:

```bash
python3 $B/proxy.py --src "$P/01_Source" --dst "$P/01_Source_Proxy" \
  --only "RYA-FX3-1107.MP4" --gate-report
```

Маска `--only` сравнивается и с именем файла, и с полным путём, так что можно
сузить до сцены: `--only "*/CAM1-FX3/*.MP4"`.

### 3. Комплект

```bash
python3 $B/proxy.py --src "$P/01_Source" --dst "$P/01_Source_Proxy" --jobs 2 \
  --report "$P/00_Setup/logs/YTCH12_proxy_report.json"
```

- `--jobs 2` по умолчанию. **Пик места = число параллельных клипов × самый большой
  прокси.** На YTCH это 3.59 ГБ (`YTCH12/RYA-FX3-0890`, оригинал 63.5 ГБ), то есть
  пик ≈ 7.2 ГБ при `--jobs 2`. Поднимать до 3 только на томе с явным запасом.
- `--bitrate auto` — битрейт по частоте кадров: 25 и 30 → 8M, 50 и 60 → 12M,
  всё остальное → 10M. По умолчанию жёсткие 8M.
- `--exclude "Scene_03,Scene_07"` — исключить сцены целиком.
- `--retries 1` по умолчанию: одна повторная попытка на клип, не сошлось второй
  раз — клип выбывает.
- Прогон **резюмируемый**: клип, который уже лежит в комплекте и проходит гейт,
  помечается `skip` и не переделывается. Поэтому упавший прогон перезапускается
  той же командой.

Долгий прогон — фоном, по канону длинных задач:

```bash
TS=$(date +%Y%m%d_%H%M)
nohup caffeinate -is python3 $B/proxy.py \
  --src "$P/01_Source" --dst "$P/01_Source_Proxy" --jobs 2 \
  --report "$P/00_Setup/logs/YTCH12_proxy_report.json" \
  > "$P/00_Setup/logs/YTCH12_proxy_$TS.log" 2>&1 &
```

### 4. Доукомплектовать — `kit.py`

Комплект обязан быть самодостаточным: открыл `.prproj`, указал на
`01_Source_Proxy` — и всё слинковалось.

```bash
python3 $B/kit.py --src "$P/01_Source" --dst "$P/01_Source_Proxy"
```

Кладёт рядом с видео петличные `*_timeline.wav`, папку `Transcription/` и
`00_LUT/`, и приводит имена лутов к канону
(`bright/normal/dark.cube` → `01_bright_scene/02_normal_scene/03_dark_scene.cube`).

⚠️ Оригиналы рекордера `*_orig*.wav` в комплект не идут: это −4.7 ГБ на проект и
монтажёру они не нужны. Их место — `99_Pipeline/DJI_Audio/` на Drive.

Только луты, без звука и транскриптов: `python3 $B/kit.py --src ... --dst ... --luts-only`.
⚠️ `--dry-run` действует **только** вместе с `--luts-only`: полное
доукомплектование сухого режима не имеет, оно и так идёт «докладывать
недостающее» и ничего не перезаписывает при совпадении размера.

### 5. Приёмка — `--verify-only`

```bash
python3 $B/proxy.py --src "$P/01_Source" --dst "$P/01_Source_Proxy" \
  --verify-only --gate-report \
  --report "$P/00_Setup/logs/YTCH12_proxy_verify.json"
```

Ничего не кодирует и не удаляет: только снимает параметры пары
источник → прокси и прогоняет гейт. Клип, которого нет в комплекте, получает
`FAIL` с текстом «прокси нет на диске».

Код возврата `proxy.py`: **0 — все клипы прошли, 1 — есть хоть один `FAIL`**
(и 1 же, если по маске ничего не нашлось). Этим удобно упираться в `&&` при
заливке: не собралось — не везём.

## Как читать отчёт из восьми пунктов

`--gate-report` печатает по клипу блок. Формат настоящий, значения ниже —
схематичные:

```
── CAM1-FX3/RYA-FX3-XXXX.MP4   [encode] тяжёлый материал с камеры: h264 140 Мбит/с, 10 бит
   ✓ разрешение   3840x2160                                      → 3840x2160
   ✓ частота      25/1                                           → 25/1
   ✓ кадры        1875                                           → 1875
   ✓ битность     yuv422p10le/High 4:2:2 (10 бит)                 → yuv420p10le/Main 10 (10 бит)
   ✓ имя и путь   CAM1-FX3/RYA-FX3-XXXX.MP4                       → CAM1-FX3/RYA-FX3-XXXX.MP4
   ✓ звук         [['pcm_s16be', 2]]                              → [['aac', 2]]
   ✓ таймкод      07:04:18:12                                     → 07:04:18:12
   ✓ теги цвета   ['', '', '']                                    → ['', '', '']
   ✓ сжатие       18.3                                            → коридор 12–25×
```

Слева всегда источник, справа — прокси. Что именно считается совпадением:

- **разрешение** — точное равенство пары чисел
- **частота** — равенство **строк** `r_frame_rate`: `30000/1001` не равно `30`
- **кадры** — равенство `nb_read_packets`; ноль или −1 слева означает, что ffprobe
  не смог посчитать пакеты источника, и это тоже `FAIL`
- **битность** — равенство **класса глубины**, а не имён форматов. `yuv422p10le` →
  `yuv420p10le` это ✓: субдискретизация имеет право поменяться, глубина — нет.
  Если глубина сошлась, но имя формата не то, которое ожидалось от профиля, в
  примечании появится «ожидали …, получили … — посмотреть руками», а пункт
  останется ✓
- **имя и путь** — относительные пути после нормализации NFC
- **звук** — равенство числа дорожек, их порядка и числа каналов в каждой. Кодек
  меняется (`pcm_s16be` → `aac`) и это нормально
- **таймкод** — если у источника TC был, у прокси обязан быть такой же; если у
  источника его нет, пункт проходит по определению. В примечании видно, откуда
  читали: у Sony это `rtmd`, у готовой прокси `tmcd`
- **теги цвета** — равенство тройки `(space, primaries, transfer)`. Пустая тройка
  слева обязана дать пустую справа
- **сжатие** — для `encode` коридор 12–25×, для `copy` побайтовое равенство размеров

Машинный вид того же лежит в `proxy_report.json`, ключ `clips[].contract`:

```json
{"frames": {"ok": true, "src": 1875, "dst": 1875, "note": "по пакетам, не по длительности"}}
```

Сводка прогона — в корне отчёта: `n`, `fails`, `frames_ok`, `total_bytes`,
`counts` (сколько `encoded` / `copied` / `skip` / `FAIL`) и `run` с параметрами
запуска.

## Клип не прошёл гейт — что делать

`proxy.py` уже сделал ретрай и удалил негодный файл, так что комплект чистый.
Дальше разбирается человек, по тому, какой именно пункт красный:

| пункт | что это значит | что делать |
|---|---|---|
| кадры | источник и прокси разной длины — обычно битый или недочитанный исходник | `ffprobe -count_packets` по источнику руками; если и он не считает — клип битый, чинить исходник, а не прокси |
| частота | в источнике VFR или дробный fps, который кодер выровнял | прогнать клип отдельно с `--gate-report`, посмотреть `r_frame_rate` источника; VFR-материал в комплект берётся через `--force copy` |
| битность | глубина не совпала | проверить, не задан ли `--chroma`/`--force encode` руками; авто-решение берёт глубину с источника и ошибиться не может |
| звук | пропала дорожка | почти всегда недекодируемая дорожка, которую не поймала проба. Клип берётся `--force copy` |
| таймкод | TC был, TC не доехал | посмотреть `timecode_src` в отчёте. Если у источника он на `rtmd`, а у прокси пусто — смотреть граблю про data-дорожку |
| теги цвета | слева пусто, справа `bt709` | кто-то запустил с `--force-bt709`. На логе это враньё в метаданных, пересобрать без флага |
| сжатие | вышло за 12–25× | ниже 12× — материал уже был лёгким, ему место в `copy`; выше 25× — исходник подозрительно тяжёлый (битый CFR-поток, длинная чёрная пауза), смотреть глазами |
| имя и путь | пути разошлись | кириллица в NFD/NFC или переименованная сцена; сверять после `norm_rel` |

Общее правило: **не чинить гейт, чинить клип**. Ослабление проверки стоит
следующего комплекта из 441 файла с тихим дефектом.

Если клип объективно особенный (VFR, экзотический звук, чужой монтаж), он
берётся `--force copy` — это законный исход, не поражение: вес такого клипа
обычно и так невелик.

## Ночная пересборка

Ставится, когда контракт поменялся и надо переделать уже сданные комплекты.
Объём на YTCH спринта 3 (замер 22.09.2026):

| проект | клипов FX3 | оригиналы | прокси сейчас |
|---|---|---|---|
| YTCH10_Anya_Yulia | 151 | 492 ГБ | 27.5 ГБ |
| YTCH11_Liza_Vitalik | 92 | 332 ГБ | 18.5 ГБ |
| YTCH12_Sveta | 115 | 225 ГБ | 12.5 ГБ |
| YTCH13_Kirill_2 | 26 | 166 ГБ | 9.3 ГБ |
| YTCH14_Katya | 23 | 123 ГБ | 6.9 ГБ |
| **итого** | **407** | **1337 ГБ** | **74.8 ГБ** |

Кодирование ≈ 5.0 ч (замер: YTCH14 = 123 ГБ за 27.2 мин при `--jobs 3`).
Заливка ≈ 13.8 ч при ~1.5 МБ/с. **Длинное плечо — заливка, а не кодирование.**

Порядок по убыванию пользы, если делать не всё сразу:
YTCH12 (в активном ревью) → YTCH11 → YTCH10 → YTCH14 → YTCH13 → Masha/Gulya.

Запуск — по одному проекту, фоном, лог в `_night_ops/logs/`:

```bash
TS=$(date +%Y%m%d_%H%M)
LOG=/Volumes/T7-Beige-RYA/YTCH/_night_ops/logs/proxy_rebuild_$TS.log
nohup caffeinate -is python3 ~/YTAI/scripts/16_proxy/1601_build/proxy.py \
  --src "$P/01_Source" --dst "$STAGE/01_Source_Proxy" --jobs 2 \
  --report "$STAGE/proxy_report.json" > "$LOG" 2>&1 &
```

`--force encode` здесь **не нужен и вреден**: авто-решение само пережмёт FX3 и
само оставит айфон в покое, а старые 8-битные прокси и так не пройдут гейт по
битности, будут удалены и собраны заново. Принудительный `encode` при этом
перемолол бы и айфон — то есть нарушил §4 контракта.

⚠️ **Место — главный риск пересборки, а не время.** На 22.09 свободно: T7-Beige
7.8 ГБ, T7-Blue-2 17 ГБ, T9-Black 32 ГБ, Macintosh HD 38 ГБ. Комплект целиком
(75 ГБ) не помещается никуда. Поэтому пересборка идёт **поштучно с перекрытием**:
клип → стейджинг на внутреннем диске (`/Users/romansergeev/YTAI_proxy_stage/`) →
гейт → заливка → удаление локального файла. Сквозной скрипт с очередью заливки —
за `1602_deliver`; пока перекрытие делается руками, по одному проекту за заход.

⚠️ Заливка 75 ГБ забивает аплинк почти на сутки и душит любые скачивания с Drive.
Ставить на время, когда канал не нужен.

⚠️ Монтажёру придётся перекачать комплект. Предупредить **до** старта, не после.

⚠️ Заливать на **те же пути** на Drive (`YTCH S3/{проект}/01_Source_Proxy/...`):
файл заменяется, ID папок сохраняются, розданные монтажёру ссылки остаются живыми.

### Как остановить

Порядок важен: сначала родитель, потом осиротевшие кодеры, потом подмести хвосты.

```bash
pkill -f '16_proxy/1601_build/proxy.py'          # 1. сам прогон
pkill -f 'hevc_videotoolbox'                     # 2. ffmpeg-дети, они переживают родителя
find "$P/01_Source_Proxy" -name '*.part.mp4' -delete   # 3. недописанные временные
find "$P/01_Source_Proxy" -name '*.part' -delete       #    то же для copy
```

Готовые клипы остаются на месте и при следующем запуске пропускаются как `skip`,
поэтому прогон продолжается той же командой. Недописанный `.part.mp4` в комплект
не попадает никогда: файл переименовывается в целевое имя только после успешного
завершения ffmpeg.

⚠️ Сторож зависаний, если он когда-нибудь появится, обязан смотреть на **движение
байтов** (сумму размеров `*.part.mp4`), а не на «давно не было готовых клипов».
21.08.2026 такой сторож убил здоровый рендер 50-гигабайтного клипа, который потом
собрался за 14 минут с первой попытки.

## Граница с Winston

Кодирование и сборку комплекта запускаем сами: операция локальная и не
деструктивная. Эскалировать Winston'у через `Task(subagent_type="winston-smith")`:

- массовую заливку комплекта на Shared Drive и всё, что упирается в квоты и права
- любое массовое удаление на Drive (медиа не удаляем — память `no-del-media`)
- разбор дублей папок и прав Shared Drive

```

{project}/00_Setup/logs/{CODE}_proxy_report.json     отчёт, схема 2
{project}/00_Setup/logs/{CODE}_proxy_verify.json     отчёт приёмки
/Volumes/T7-Beige-RYA/YTCH/_night_ops/logs/          канальные ночные прогоны
```

Никогда `/tmp`. Лог живёт на том же томе, что и материал: прогон запустил человек,
он же и смотрит, а отмонтированный вместе с диском лог никому не мешает.

⚠️ Для launchd-агента так делать **нельзя**: `StandardOutPath` на `/Volumes/…`
даёт `EX_CONFIG 78` ещё до старта python, и лог не появляется вовсе. Логи агентов —
только `~/Library/Logs/ytai/`.
