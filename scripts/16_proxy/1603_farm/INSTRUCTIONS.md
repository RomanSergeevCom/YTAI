# 1603_farm — фабрика прокси, работающая от Drive

Третий драйвер этапа `16_proxy`. Контракт из восьми пунктов у всех трёх один и
тот же — `1601_build/contract.py`; различается только логистика.

| драйвер | откуда берёт | куда кладёт | когда нужен |
|---|---|---|---|
| `1601_build/proxy.py` | локальная папка | локальная папка | один проект, место есть |
| `1601_build/rebuild.py` | локальный SSD | Drive внахлёст | канал целиком, места нет |
| **`1603_farm/farm.py`** | **Drive** | **Drive** | **машины и дисков рядом нет** |

Фабрика решает задачу, которую не решают первые два: собрать прокси, **не завися
от того, где физически лежат диски и где находится Роман**. Исходники берутся с
Drive, готовые прокси уезжают на Drive, локально в любой момент живёт только
хвост очереди. Отсюда два следствия, ради которых всё и делалось:

- **карту можно чистить.** Манифест один раз доказал, что каждый исходник лежит
  на Drive по имени и точному размеру. После этого карта фабрике не нужна;
- **симлинки перестают быть препятствием.** Фабрика кодирует настоящий файл,
  скачанный с Drive, а не ссылку.

---

## Как это устроено

```
plan.py    там, где смонтированы диски: строит манифест «сцена → файл на Drive»,
           проверяет КАЖДЫЙ источник по точному размеру и кладёт манифест на Drive
             ↓  _farm_plan.json рядом с комплектом
farm.py    где угодно: читает манифест, ведёт очередь, гонит клипы
             ├── store.py   журнал-истина, производный индекс, лизы
             ├── drive.py   rclone: снимок, скачивание, заливка, сверка
             └── contract.py (1601_build)   решение, команда, ГЕЙТ
```

Один клип проходит: `взять из очереди → скачать → снять параметры → решить →
собрать → ГЕЙТ → залить → подтвердить размером с Drive → убрать за собой`.

---

## Шесть свойств, из которых растёт устойчивость

**1. Истина о сделанном — на Drive, а не в состоянии.**
Клип сделан, если прокси лежит на месте и проходит контракт. Очередь на диске —
кэш для дешёвого возобновления. Потеряется целиком — прогон восстановится по
одному снимку Drive. Ничего незаменимого на рабочей машине не живёт.

**2. Очередь — журнал, который только дописывается.**
`journal.jsonl`, одна запись в строку, `fsync` после каждой. Записанное никогда
не перезаписывается, поэтому испортить его нечем. `index.json` — производный кэш,
пишется атомарно (временный файл + `replace`) и источником правды не считается.
Битая строка журнала пропускается поимённо и не обнуляет ночь работы.

**3. Клип не теряется и не делается дважды.**
Взятый клип получает лизу на 3 часа. Воркер упал, машина перезагрузилась,
процесс убит — лиза истекает, и клип возвращается в очередь сам. Ручной расчистки
«подвисших» записей нет как класса.

**4. Место — обратное давление, а не надежда.**
Резерв считается на **оба** файла: скачанный оригинал (у FX3 бывает 52 ГБ) и
прокси. Кодировщик блокируется на `reserve()`, пока некуда класть, — это
правильная форма прогона, а не зависание, и сторож это знает.
До `probe` оценка пессимистична (÷10), после — честная: длительность × заказанный
битрейт. ⚠️ Отношение «×18» годится только для 25p на 8 Мбит/с; для 50p
заказывается 12 Мбит/с, и ×18 занижает вес на четверть.

**5. Приговор выносит гейт, а не наш отчёт.**
Не сошёлся хоть один из восьми пунктов — клип **не уезжает**. А залитое
подтверждается размером, полученным **с Drive**, а не тем, что rclone не ругнулся.

**6. Исходники не удаляются никогда.**
Удаляется только то, что фабрика сама скачала в стейджинг, и только после
подтверждённой заливки. Локальный исходник — чужой файл, его не трогают ни при
каком исходе.

## Команды

```bash
# регрессия — без неё правка не уезжает ни в коммит, ни в ночь
python3 farm.py selftest

# манифест: ТАМ, где смонтированы диски
python3 plan.py --unit YTEVO03                 построить и проверить
python3 plan.py --unit YTEVO03 --publish       выгрузить на Drive

# прогон: где угодно
python3 farm.py run --unit YTEVO03 --dry-run   что и почему будет сделано
python3 farm.py run --unit YTEVO03             боевой
python3 farm.py status --unit YTEVO03          где стоим
python3 farm.py revive --unit YTEVO03          вернуть отложенное в очередь
```

### Выключатели — файлами, без убийства процесса

```bash
touch ~/.cache/ytai/proxy_farm/STOP            остановиться, очередь цела
touch ~/.cache/ytai/proxy_farm/PAUSE_UPLOAD    кодировать, но не лить
rm ~/.cache/ytai/proxy_farm/STOP               снять
```

### На Мемексе

```bash
bash deploy_memex.sh          развернуть: код, регрессия на месте, launchd, сторож
bash deploy_memex.sh --check  только проверить

ssh memex 'export PATH=/opt/homebrew/bin:$PATH; launchctl kickstart -p gui/$(id -u)/ae.rya.ytai-proxy-farm'
```

⚠️ **В неинтерактивном ssh PATH без Homebrew** — `ffmpeg`, `rclone` и `python3`
«исчезают». `export PATH=/opt/homebrew/bin:$PATH` нужен в каждой команде; в plist
он прописан отдельным ключом.

`launchd`: ночной запуск в 01:00, сторож раз в 15 минут. **`KeepAlive` сознательно
не ставится**: фабрика сама выходит с кодом 0, когда работы нет, и `KeepAlive`
крутил бы её по кругу, сжигая квоту Drive на снимках.

## Грабли, уже оплаченные

- ⚠️ **`rclone` не принимает фильтры в операциях над ОДНИМ файлом.** `copyto` с
  `--exclude` падает насмерть: `can't limit to single files when using filters`.
  Этим же `copyto` идут и скачивание, и заливка каждого клипа. `drive.flags()`
  разводит два набора флагов, и это проверяется регрессией.
- ⚠️ **`--bitrate` обязан быть `auto`.** У `proxy.py` дефолт — `8M`, а
  `bitrate_for()` отдаёт override как есть: таблица `FPS_BITRATE` тогда не
  работает вовсе. На YTEVO03 это увело бы 109 клипов 50p на 8 Мбит/с вместо 12,
  и гейт бы промолчал — его коридор 0.35–2.5× это пропускает.
- ⚠️ **У сухого прогона свой журнал.** Общий он бы отравил: сухой прогон помечает
  клипы сделанными, ничего не собрав, и боевой после него отчитался бы зелёным,
  не собрав ни одного клипа.
- ⚠️ **Снимок Drive, который не снялся, — не пустая папка.** Пустой снимок
  означал бы «на Drive нет ничего» и запустил бы пересборку всего уже готового.
  Не снялся — прогон отменяется и говорит об этом вслух.
- ⚠️ **Квота Drive (750 ГБ/сутки) не лечится повтором** — только ожиданием.
  Клип возвращается в очередь, попытка не тратится.
- ⚠️ **Заливка только `copyto`/`copy`, никогда `sync`.** В комплекте на Drive
  живут не только видео: у YTEVO03 там 277 транскриптов, и это их единственная
  копия вне `_work`. `sync` снёс бы их.
- ⚠️ **Флаг нагрузки для сторожа температуры.** Фабрика зовёт `~/bin/ytai_load`,
  иначе сторож Мемекса поднимет ложную тревогу «горячо» на каждом ночном прогоне,
  и Роман перестанет читать его сообщения.
- ⚠️ **`--jobs` почти не помогает:** `hevc_videotoolbox` — один аппаратный блок.
  Замер: один поток ×3.7 реалтайма, три потока ×4.0. Зато каждый воркер требует
  своей площадки под оригинал+прокси. Дефолт — один.

## Что чинилось в контракте вместе с этим (23.09.2026)

- `contract.py` — спаннер опознаётся **по имени** (`__S##`), а не по
  `os.path.islink`. Прежний признак врал в обе стороны: у YTCH спаннеры —
  обычные файлы, и он не срабатывал вовсе; у съёмочных дней симлинками являются
  **все** исходники, и на YTEVO03 прогон объявлял спаннерами все 172 клипа,
  собирал ноль и отчитывался «пропущено 172», а приёмка считала это законным.
- `audit.py` — перестал выбрасывать симлинки. Раньше «проверь прокси» по
  YTEVO03 показывало 0 клипов вместо 172, то есть отвечало «всё хорошо» там,
  где не проверило ничего.
- `contract.py` — исправлен комментарий про таймкод. Замер по 172 прокси:
  `format_tags=timecode` несут **ноль** из них, обещанного «дублирования» нет.
